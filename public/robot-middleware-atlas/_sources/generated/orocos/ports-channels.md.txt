# Port 与 ChannelElement：连接策略、数据所有权和 FlowStatus

```{contents} Contents
:depth: 2
:local:
```


RTT 的 Port 负责类型与连接入口，真正的读写行为由 ChannelElement 链和 ConnPolicy 组合。理解这一层，才能回答 `write()` 是否复制、`readNewest()` 为什么可能线性耗时，以及 buffer 满时丢哪一条。

源码入口：[`InputPort.hpp`](https://github.com/orocos-toolchain/rtt/blob/600102e8be9c81905b20930e32d43b28244ab173/rtt/InputPort.hpp)、[`OutputPort.hpp`](https://github.com/orocos-toolchain/rtt/blob/600102e8be9c81905b20930e32d43b28244ab173/rtt/OutputPort.hpp) 与 [`ConnPolicy.hpp`](https://github.com/orocos-toolchain/rtt/blob/600102e8be9c81905b20930e32d43b28244ab173/rtt/ConnPolicy.hpp)。

可以先放进一个控制场景。关节估计器每 1 ms 写出 `JointState`，控制组件只需要最新状态；轨迹规划器偶尔写入一段必须按顺序执行的 `TrajectoryPoint`。两者都能使用 Port，但不应该使用相同连接策略：前者积压历史会增加数据年龄，后者覆盖旧项会改变轨迹含义。

```text
OutputPort<T>::write(sample)
  -> output endpoint
  -> one or more ChannelElement<T>
       -> DATA object / BUFFER storage / transport element
  -> input endpoint
  -> InputPort<T>::read(sample)
```

Port 是端点，不是队列本身。连接建立时，factory 才依据 `ConnPolicy` 选择单值 DataObject、FIFO Buffer、同步方法以及本地或远程 ChannelElement。本文固定阅读 RTT 提交 [`600102e8be9c81905b20930e32d43b28244ab173`](https://github.com/orocos-toolchain/rtt/tree/600102e8be9c81905b20930e32d43b28244ab173)。

## 类型化 Port 建立静态边界

```cpp
RTT::OutputPort<JointState> out("state");
RTT::InputPort<JointState> in("state");

RTT::ConnPolicy policy = RTT::ConnPolicy::data();
out.connectTo(&in, policy);
```

模板参数 `JointState` 让同进程连接在编译期确定数据类型。类型擦除接口用于部署和反射，实际读写最终回到类型化 data source/channel endpoint。

一个 OutputPort 可以连接多个输入，因此一次 write 可能扇出到多条 channel。各连接可以有不同 ConnPolicy；慢连接是否会占用发布者线程，必须继续查看 fan-out 循环和具体下游 element，不能仅从 Port API 推断。

真实的 [`OutputPort<T>::write()`](https://github.com/orocos-toolchain/rtt/blob/600102e8be9c81905b20930e32d43b28244ab173/rtt/OutputPort.hpp#L243-L263) 很短：

```cpp
WriteStatus write(const T& sample)
{
    if (keeps_last_written_value || keeps_next_written_value) {
        keeps_next_written_value = false;
        has_initial_sample = true;
        this->sample->Set(sample);
    }
    has_last_written_value = keeps_last_written_value;

    WriteStatus result = NotConnected;
    if (connected()) {
        traceWrite();
        result = getEndpoint()->getWriteEndpoint()->write(sample);
    }
    return result;
}
```

先看 C++ 语法。`const T&` 表示函数借用调用方的样本，不能通过这只引用修改原对象，也不会仅因为传参就复制一次 `T`。真正的复制可能发生在 `sample->Set(sample)`、DATA storage、BUFFER slot 或 transport serialization 中。

`this->sample` 不是当前参数，而是 OutputPort 可选保存的“最后写入样本”。只有启用 `keepLastWrittenValue()` 或下一次保留标志时才更新它；`ConnPolicy::init` 也只有在 writer 确实保留了最后值时，才可能用该值初始化新连接。随后代码取得 write endpoint，将类型化调用交给 ChannelElement 链。

## ConnPolicy 描述语义而不是实现类名

关键字段包括：

- `type`：DATA 或 BUFFER；
- `size`：有界队列容量；
- `lock_policy`：LOCKED、LOCK_FREE 或 UNSYNC；
- `pull`：PUSH 或 PULL 方向；
- `init`：连接建立后是否提供初始样本；
- `mandatory`：某些传输场景的强制连接语义；
- transport/name/data_size 等远程连接信息。

Policy 是配置值对象，channel factory 根据它建立具体元素链。这样公开 Port 不依赖 `BufferLockFree<T>` 等实现类型。

这个“值对象变成运行时对象”的位置在 [`ConnFactory::buildDataStorage<T>()`](https://github.com/orocos-toolchain/rtt/blob/600102e8be9c81905b20930e32d43b28244ab173/rtt/internal/ConnFactory.hpp#L160-L209)：

```cpp
if (policy.type == ConnPolicy::DATA) {
    DataObjectInterface<T>::shared_ptr data_object;
    switch (policy.lock_policy) {
      case ConnPolicy::LOCK_FREE:
        data_object.reset(new DataObjectLockFree<T>(initial_value, policy));
        break;
      case ConnPolicy::LOCKED:
        data_object.reset(new DataObjectLocked<T>(initial_value));
        break;
      case ConnPolicy::UNSYNC:
        data_object.reset(new DataObjectUnSync<T>(initial_value));
        break;
    }
    return new ChannelDataElement<T>(data_object, policy);
}

if (policy.type == ConnPolicy::BUFFER ||
    policy.type == ConnPolicy::CIRCULAR_BUFFER) {
    // 同样根据 lock_policy 选择 BufferLockFree / Locked / UnSync
    return new ChannelBufferElement<T>(buffer_object, policy);
}
```

这里同时展示了模板、运行时分支和多态的分工。模板参数 `T` 让 factory 能构造正确的 `DataObjectLockFree<T>`；`policy.type` 和 `lock_policy` 则允许运行时配置选择实现；返回的基类 ChannelElement 让后续链路不需要知道具体 storage 类名。

`shared_ptr` 在这个版本中是 RTT/Boost 风格的共享句柄。它表示 ChannelElement 与其他连接对象可以共同延长 storage 寿命，但引用计数只管理销毁，不会自动让 `T` 的复制变成实时安全。若 `T` 内部包含会扩容的 `std::vector`，lock-free 外壳仍可能在赋值时进入分配器。

## PUSH 与 PULL 改变谁承担复制

PUSH 连接由 writer 主动把样本送入下游存储：

```text
OutputPort::write(sample)
  -> channel.write(sample)
  -> input-side storage updated
```

PULL 连接则让 reader 在读取时向上游请求当前值：

```text
InputPort::read(sample)
  -> channel.read(sample)
  -> upstream data source supplies value
```

PUSH 的发布延迟包含所有下游写入，读取便宜；PULL 写入便宜，读取时承担上游访问，并可能跨越不合适的线程边界。控制回路通常偏好明确的 PUSH 与本地有界存储。

固定版本的 `ConnPolicy` 文档把 `pull` 的主要效果限定在多进程通信。本地连接怎样布置 buffer 还会受到 `buffer_policy` 影响，因此不能仅凭 `pull=true` 推导整条进程内对象图。能够确定的是：无论 PUSH 还是 PULL，reader 侧都通过 ChannelElement 的 `signal()` 获知新数据可用。

## 扇出在调用者线程中逐连接执行

一个 OutputPort 连接多个输入时，真实的 [`MultipleOutputsChannelElement<T>::write()`](https://github.com/orocos-toolchain/rtt/blob/600102e8be9c81905b20930e32d43b28244ab173/rtt/base/ChannelElement.hpp#L297-L325) 会遍历全部输出：

```cpp
WriteStatus result = WriteSuccess;
RTT::os::SharedMutexLock lock(outputs_lock);
if (outputs.empty()) return NotConnected;

for (Outputs::iterator it = outputs.begin(); it != outputs.end(); ++it) {
    ChannelElement<T>::shared_ptr output = it->channel->narrow<T>();
    WriteStatus fs = output->write(sample);
    if (it->mandatory && (result < fs)) result = fs;
    if (fs == NotConnected) it->disconnected = true;
}
```

这段代码没有建立后台广播任务。调用 `OutputPort::write()` 的线程持有共享读锁，按连接顺序调用每个下游。于是写入成本至少随连接数线性增长；某个 transport 或同步 storage 的慢路径也会占用当前调用线程。循环结束后，实现再清除被标记为断开的输出。

`mandatory` 决定下游失败是否升级为整个 write 的返回失败。非 mandatory 连接可以失败而不把每次局部状态都暴露成顶层失败；这有利于可选监控端脱落时保持控制链运行，却意味着应用若需要逐连接诊断，还必须读取连接状态和统计，而不能只看一个 `WriteStatus`。

## DATA 是单值状态对象

DATA connection 保存当前值和新旧状态。连续写入 A、B、C 而读者只读一次时，通常观察 C；中间历史不是该策略的契约。

[`ChannelDataElement<T>`](https://github.com/orocos-toolchain/rtt/blob/600102e8be9c81905b20930e32d43b28244ab173/rtt/internal/ChannelDataElement.hpp#L56-L91) 只是把操作委托给选中的 DataObject：

```cpp
WriteStatus write(param_t sample) override {
    if (!data->Set(sample)) return WriteFailure;
    return this->signal() ? WriteSuccess : NotConnected;
}

FlowStatus read(reference_t sample, bool copy_old_data) override {
    return data->Get(sample, copy_old_data);
}
```

`param_t` 与 `reference_t` 是 `ChannelElement<T>` 根据类型特征定义的参数形式，可把它们理解为“适合传入 `T` 的只读形式”和“能够被 read 写入的形式”。这种 typedef 能为小标量和大对象选择不同传参方式，但不会改变连接的值语义：storage 仍要在 writer 返回后独立保存可读样本。

读接口的 `copy_old` 参数决定没有新值时是否复制旧值：

```cpp
FlowStatus status = input.read(sample, true);
```

若返回 `OldData`，`sample` 可被填为上次值；若 `copy_old=false`，调用方不能假设输出对象已更新。

## BUFFER 与 CIRCULAR_BUFFER 的丢弃方向

有界队列容量为 3：

```text
BUFFER 满载 [A B C] + D -> 保留 [A B C]，D 失败/被丢弃
CIRCULAR     [A B C] + D -> 保留 [B C D]，A 被覆盖
```

普通 BUFFER 保护已经接收的历史，适合命令与事件；CIRCULAR 保护新鲜度，适合状态流。两者空间都是 `O(capacity × sizeof(T))`，push/pop 目标为 `O(1)`。

系统必须暴露 dropped counter。没有计数时，消费者只看到数据继续到来，无法判断是否跨过了若干关键状态。

RTT 的 [`ChannelBufferElement<T>`](https://github.com/orocos-toolchain/rtt/blob/600102e8be9c81905b20930e32d43b28244ab173/rtt/internal/ChannelBufferElement.hpp#L58-L153) 确实公开 `capacity()`、当前 `size()` 和 `dropped()`，写入与读取主干如下：

```cpp
WriteStatus write(param_t sample) override {
    if (!buffer->Push(sample)) return WriteFailure;
    return this->signal() ? WriteSuccess : NotConnected;
}

FlowStatus read(reference_t sample, bool copy_old_data) override {
    value_t* next = buffer->PopWithoutRelease();
    if (next) {
        if (last_sample_p) buffer->Release(last_sample_p);
        sample = *next;
        if (policy.buffer_policy != PerOutputPort &&
            policy.buffer_policy != Shared)
            last_sample_p = next;
        else
            buffer->Release(next);
        return NewData;
    }
    if (last_sample_p) {
        if (copy_old_data) sample = *last_sample_p;
        return OldData;
    }
    return NoData;
}
```

这里最容易忽略的是 `PopWithoutRelease()`。buffer 先把 slot 的指针交给 ChannelElement，后者完成 `sample = *next` 后，仍可能保留该 slot 作为 `OldData` 来源；下一次读到新值或析构时才 `Release`。因此“从 FIFO pop”不一定意味着槽位当场回到 producer。

源码还会根据 `buffer_policy` 决定是否保存 `last_sample_p`。多个 reader 共享 buffer 时，永久扣住同一 slot 会改变其他 reader 的可见性，所以某些策略会在复制后立即释放，并且不再承诺返回 `OldData`。这说明 FlowStatus 不只由 BUFFER/DATA 决定，还与连接共享方式有关。

## `readNewest()` 通过 drain 获得最新值

真实的 [`InputPort<T>::readNewest()`](https://github.com/orocos-toolchain/rtt/blob/600102e8be9c81905b20930e32d43b28244ab173/rtt/InputPort.hpp#L158-L166) 是：

```cpp
FlowStatus readNewest(reference_t sample, bool copy_old_data = true) {
    FlowStatus result = read(sample, copy_old_data);
    if (result != RTT::NewData)
        return result;

    while (read(sample, false) == RTT::NewData);
    return RTT::NewData;
}
```

它会反复消费 backlog。队列中有 `N` 条时，它是 `O(N)`，不是对尾元素的 `O(1)` peek。第二次开始传入 `copy_old_data=false`，因为循环只想继续取新项，不需要在队列已经清空后再复制一次旧样本。若生产速度持续超过 drain 速度，单周期读成本会失去上界。

需要恒定时间最新值时应选择 DATA，或设计能原子替换最新快照的结构，而不是用大 BUFFER 加 `readNewest()` 模拟。

## Lock-free DataObject 使用多槽避免读写同一对象

概念上，writer 寻找未被 reader 占用的槽位，写完后发布新的 current index；reader 增加槽位读计数，复制完成后减少：

```text
slots: [0][1][2]
current = 1
reader: pin slot 1 -> copy -> unpin
writer: choose slot != current and readers==0 -> assign -> publish index
```

多个槽位避免 writer 原地修改 reader 正在复制的 `T`。但 writer 可能需要扫描槽位；读者长期持有也会减少可用槽。lock-free 保证系统中总有线程推进，不保证每次调用固定步骤完成。

## 样本类型决定隐藏成本

对 `std::vector<double>`，赋值可能重新分配。改进方法包括：

- configure 阶段 reserve 固定上限；
- 使用固定容量数组或 bounded vector；
- 用 loaned buffer/引用计数块传递大 payload；
- 将元数据和大块存储分离，队列只移动句柄。

零拷贝句柄会增加生命周期复杂度：producer 不能在最后一个 consumer 释放前复用内存，慢 consumer 会耗尽 buffer pool。因此必须设定 pool 数和耗尽策略。

## ChannelElement 链的故障传播

[`WriteStatus`](https://github.com/orocos-toolchain/rtt/blob/600102e8be9c81905b20930e32d43b28244ab173/rtt/FlowStatus.hpp#L56-L66) 只有三个公开状态：`WriteSuccess`、`WriteFailure` 和 `NotConnected`。它表达当前调用是否成功进入连接，而不是远端业务是否已经处理样本。ChannelElement 基类文档也明确说明，写成功不能推出另一端已经收到。

链上 storage 满载会返回 `WriteFailure`，下游失效会返回 `NotConnected`。扇出层只把 mandatory 连接的失败合并到顶层状态，同时标记断开的 channel，循环结束后调用 `removeDisconnectedOutputs()`。因此一个状态值不能还原每条连接发生了什么；工程诊断仍需连接级 dropped、fill level、断开和 transport 统计。

固定版本并不是“锁内复制连接快照、锁外逐一发送”，而是在 `outputs_lock` 的共享锁域内遍历并调用下游。共享锁允许并发 writer 读取同一连接表，却会阻塞需要修改连接集合的独占操作。若下游 write 很慢，断开或重连也可能更晚取得写锁。这是 fan-out 简单直接的代价。

## 连接关闭必须等待在途读写离开

Port、endpoint、ChannelElement 和 storage 形成跨对象链。若一端在另一线程仍执行 `write()` 或 `read()` 时直接释放中间 element，就会产生悬空指针；如果为了避免悬空而让双方永久共享，又可能形成不能回收的环。

RTT 使用 intrusive/shared handle 延长在途 ChannelElement 的寿命，并让连接管理器负责从两端关系中拆除链路。应用层仍应遵循更大的关闭顺序：

```text
停止产生新的 updateHook / write
  -> 唤醒并停止 Activity
  -> 等待执行线程退出
  -> 断开 Port connections
  -> 释放 ChannelElement 与 storage
  -> 析构 TaskContext 的 Port 成员
```

若先断开 Port，再等待组件线程停止，正在运行的 `updateHook()` 可能恰好访问已经拆除的 endpoint。若只停线程却不解除远程 transport，后台接收又可能继续 signal 输入端。安全关闭需要同时封住新的生产、等待在途执行，并按依赖逆序销毁。

## 数据路径性能表

| 操作 | 典型复杂度 | 最坏风险 |
|---|---:|---|
| DATA write/read | 近似 `O(1)` + `T` 复制 | 大对象分配、reader pin 延长 |
| BUFFER push/pop | `O(1)` + `T` 复制 | 满队列丢新或阻塞策略 |
| CIRCULAR push/pop | `O(1)` + `T` 复制 | 覆盖旧数据不可追溯 |
| `readNewest` | `O(backlog)` | 输入风暴耗尽周期预算 |
| OutputPort fan-out | `O(connections)` | 一个慢 channel 放大发布延迟 |

端口性能报告必须说明 payload 类型、连接数、policy、是否同进程、是否预分配以及 drop 行为；只有消息/秒没有可比性。

## 设计取舍与适用边界

Port 与 storage 分离，使同一个 `InputPort<T>` 可以在部署时选择 DATA、BUFFER、同步算法和 transport；模板又把类型错误尽量提前到编译期。这种组合能力非常适合组件化机器人系统，因为算法类不必为“本地最新值”和“跨进程事件队列”各写一套接口。

代价是运行语义不能只从 C++ 成员类型看出来。两个完全相同的 `InputPort<JointState>`，可能拥有不同容量、丢弃方向、复制成本和线程影响。部署配置成为程序行为的一部分，必须与源码一起版本化和评审。

LOCK_FREE 也不是实时性的同义词：容器可能具有系统级进展保证，`T` 的复制却仍会分配；`readNewest()` 可以使用 lock-free buffer，却仍随 backlog 线性增长；远程 ChannelElement 还会引入序列化、内核队列和网络故障。只有把类型、连接数、policy、Activity 优先级和最坏执行时间合在一起，才能判断控制周期是否可行。

## 最小复刻从两种 storage 开始

若要自行实现这一层，不要先做反射和远程 transport。第一版只需要：

```cpp
enum class FlowStatus { NoData, OldData, NewData };
enum class WriteStatus { Success, Full, Disconnected };

template<class T>
class Storage {
 public:
  virtual WriteStatus Write(const T&) = 0;
  virtual FlowStatus Read(T&, bool copy_old) = 0;
  virtual ~Storage() = default;
};
```

按以下顺序扩展：

1. 实现 `LatestValue<T>`，证明连续写入后只读取最新值，并区分 `NewData/OldData/NoData`；
2. 实现固定容量 `Fifo<T>`，分别测试满载丢新和循环覆盖旧值；
3. 给 Output endpoint 加连接数组，定义 mandatory 失败聚合和断开清理；
4. 给每条连接加入 fill、drop、write-failure 和最大写耗时统计；
5. 加入通知回调，但保证用户逻辑不在连接表独占锁内执行；
6. 最后才加入 type erasure、动态 factory 和远程 transport。

完成标准不只是 A 能把数字传给 B。至少要证明：满载方向固定；旧值复制契约明确；扇出中一个可选连接失败不会伪装成全部失败；断开与并发 write 不产生 use-after-free；停止后不再 signal 已销毁的 InputPort；固定容量类型在稳定态不分配。
